## 功能需求清单

- **FR1 – 全局阈值治理：** 超级管理员可创建、编辑并发布血压与心率的健康阈值，系统始终执行硬性输入范围。
- **FR2 – 版本历史：** 超级管理员可查看阈值变更记录（操作人、时间、前后差异）。
- **FR3 – 安全预览：** 发布前可在示例数据中预览新阈值对“异常/正常”判定的影响。
- **FR4 – 即时下发：** 新阈值发布后，会同步至所有家庭仪表盘与后端服务，无需用户重新登录。
- **FR5 – 录入校验：** 新增/编辑健康记录时，表单提示当前阈值下的状态，并阻止超出 30–250 mmHg 与 30–150 bpm 的非法输入。
- **FR6 – 仪表盘高亮：** 仪表盘用颜色、徽标和无障碍标签突出异常读数。
- **FR7 – 历史洞察：** 用户可按“正常 / 异常”筛选历史趋势，快速发现模式变化。
- **FR8 – API 输出：** 外部接口与导出文件包含读数“状态”字段，反映生成时的阈值配置。
- **FR9 – Self/自己 保护：** 阈值逻辑对“Self/自己”成员同样适用，同时保持其不可删除/修改的保护策略。
- **FR10 – 审计导出：** 超级管理员可导出阈值配置的历史 CSV/JSON 用于合规审查。

## 史诗与用户故事明细

### 史诗 1：超级管理员阈值治理中心

**目标价值：** 让超级管理员以安全、透明的方式管理阈值配置，确保存档与发布流程可追溯、可回滚。

#### 故事 1.1：阈值配置界面

作为一名超级管理员，我希望在后台表单中管理收缩压、舒张压与心率阈值，这样可以快速对齐医疗标准。

**Acceptance Criteria:**

- **Given** 超级管理员已登录后台  
	**When** 点击侧边导航中的 “Super Admin Setting”  
	**Then** 能看到当前阈值及单位、说明文本与最后更新时间
- **And** 输入新阈值时，系统执行上下限校验并提供即时错误提示
- **And** 表单保存成功后提示“待发布”状态

**Prerequisites：** 无（史诗启动项）。

**Technical Notes：** 使用 Ant Design `Form` + `InputNumber`；路由 `/super-admin/settings` 仅超级管理员可访问；前端调用 `/api/v1/admin/thresholds/draft`；后端按 Flask Blueprints 规则写入配置表 `threshold_profiles`。

#### 故事 1.2：阈值版本列表与比对

作为超级管理员，我希望查看历史版本及差异，这样能追踪是谁调整了阈值。

**Acceptance Criteria:**

- **Given** 存在历史阈值版本  
	**When** 管理员打开“版本记录”页签  
	**Then** 列表显示提交人、时间、阈值数值与备注
- **And** 选择两个版本时，系统以高亮方式展示阈值差异
- **And** 列表支持按日期、操作者搜索过滤

**Prerequisites：** 故事 1.1。

**Technical Notes：** 新建表 `threshold_versions` 记录 JSON 值；前端使用 `Table` 与对比面板；后端提供 `/api/v1/admin/thresholds/versions` GET。

#### 故事 1.3：阈值调整预览

作为超级管理员，我希望发布前看到阈值对典型读数的影响，这样可以避免误配置。

**Acceptance Criteria:**

- **Given** 管理员已填写新的阈值草稿  
	**When** 点击“预览影响”  
	**Then** 系统显示样例读数（最近 30 条）及其状态（健康/临界/异常）
- **And** 支持导入 CSV 作为预览样例
- **And** 若阈值导致全部异常，系统给出二次确认提示

**Prerequisites：** 故事 1.1。

**Technical Notes：** 后端暂存草稿阈值在 Redis；预览接口批量判定状态；前端以 `Drawer` 呈现图表与表格。

#### 故事 1.4：阈值变更审计

作为安全审计员，我希望所有阈值变更都记录在日志中，这样可以满足合规要求。

**Acceptance Criteria:**

- **Given** 有管理员发布阈值  
	**When** 发布动作完成  
	**Then** 审计日志写入操作者、IP、User-Agent、修改前后值、备注
- **And** 管理员可在“审计导出”页面下载指定时间段的 CSV/JSON
- **And** 导出文件遵循 UTF-8 BOM 且含阈值版本号

**Prerequisites：** 故事 1.2。

**Technical Notes：** 复用现有 `audit_log` 中间件；新增 `threshold` 事件类型；导出接口 `/api/v1/admin/thresholds/audit/export` 限速。

#### 故事 1.5：导航与权限调整

作为体验负责人，我希望侧边导航能准确反映不同角色的设置入口，这样用户不会混淆个人设置与超级管理员配置。

**Acceptance Criteria:**

- **Given** 普通用户或管理员登录  
	**When** 查看侧边菜单  
	**Then** “Settings” 菜单被重命名为 “User Setting”，菜单仅显示用户语言与密码修改功能
- **And** “User Management” 菜单保持原名和权限，仅超级管理员和管理员可见
- **And** 只有超级管理员能看到新的 “Super Admin Setting” 菜单项，进入后展示阈值管理功能

**Prerequisites：** 故事 1.1。

**Technical Notes：** 更新前端路由与侧边栏配置；统一使用 i18n key `menu.userSetting`、`menu.userManagement`、`menu.superAdminSetting`；在权限钩子中检查角色 `role == 'super_admin'`。

### 史诗 2：阈值发布与跨系统同步

**目标价值：** 确保阈值发布后在后端、缓存、API 与家庭成员视图中一致生效，并持续保护 Self/自己 成员。

#### 故事 2.1：阈值发布与缓存失效

作为超级管理员，我希望一次点击即可发布新阈值，并快速同步到所有服务。

**Acceptance Criteria:**

- **Given** 草稿阈值已保存  
	**When** 管理员点击“发布”  
	**Then** 后端将草稿标记为 Active 并写入主配置表
- **And** 系统在 5 秒内广播缓存失效（Redis pub/sub）
- **And** 发布成功后在 UI 显示版本号与生效时间

**Prerequisites：** 故事 1.4。

**Technical Notes：** 使用 Redis channel `threshold.invalidate`；后端服务在 `extensions.py` 注册订阅器；记录版本号 `threshold_version`。

#### 故事 2.2：阈值状态 API 输出

作为集成开发者，我希望 API 和导出数据能带上阈值状态信息，便于下游应用识别读数健康情况。

**Acceptance Criteria:**

- **Given** 阈值发布为最新版  
	**When** 调用健康记录列表 API 或导出 CSV  
	**Then** 每条数据包含 `threshold_status`（healthy/borderline/out_of_range）与 `threshold_version`
- **And** 文档在 OpenAPI 定义中列出状态枚举与示例
- **And** 若阈值缺失，API 返回 503 并包含故障排查提示

**Prerequisites：** 故事 2.1。

**Technical Notes：** 扩展 `/api/v1/health-records` 序列化器；更新 `frontend/src/services/api.js`；新增数据迁移补充字段。

#### 故事 2.3：Self/自己 阈值保护策略

作为平台管理员，我希望 Self/自己 成员持续受到保护，不受阈值配置影响其核心属性。

**Acceptance Criteria:**

- **Given** 阈值发布后  
	**When** 针对 Self/自己 成员请求修改阈值或删除成员  
	**Then** 后端拒绝操作并返回特定错误码 `SELF_PROTECTED`
- **And** 仪表盘依然对 Self/自己 的读数进行阈值计算与展示
- **And** 审计日志记录所有对 Self/自己 的违规尝试

**Prerequisites：** 故事 2.1。

**Technical Notes：** 在 `manager/member_manager.py` 加条件；新增守护测试；API 返回 400 + i18n 文案；审计事件类型 `self_threshold_blocked`。

### 史诗 3：家庭成员体验与可视化

**目标价值：** 为家庭成员提供准确、友好的录入与查看体验，让异常读数即时可见并易于追踪。

#### 故事 3.1：录入表单实时状态提示

作为家庭成员，我希望在录入血压或心率时即时看到状态提醒，以便及时调整。

**Acceptance Criteria:**

- **Given** 用户打开“新增健康记录”表单  
	**When** 输入读数  
	**Then** 表单下方显示状态徽章（绿色/橙色/红色）及文字说明
- **And** 超出硬性范围时，保存按钮禁用并提示“请联系医生确认”
- **And** 页面遵循 WCAG 键盘可访问性

**Prerequisites：** 故事 2.1。

**Technical Notes：** 前端调用 `/api/v1/thresholds/active` 缓存 60 秒；使用 `useDebounce` 控制请求；表单组件添加 ARIA 标签。

#### 故事 3.2：仪表盘异常高亮与无障碍提示

作为家庭成员，我希望仪表盘能清楚标识异常读数并提供说明。

**Acceptance Criteria:**

- **Given** 仪表盘加载最近 30 天读数  
	**When** 存在越界数据  
	**Then** 图表节点与列表行使用高对比度颜色，并附加状态标签与工具提示
- **And** 工具提示显示当前阈值区间、上次更新时间与版本号
- **And** 屏幕阅读器朗读状态并指向帮助文档

**Prerequisites：** 故事 3.1。

**Technical Notes：** 使用 ECharts 自定义 `itemStyle`; 添加 `aria.enabled=true`; 工具提示引用 `threshold_version`；更新 i18n 文案。

#### 故事 3.3：历史视图按状态筛选

作为家庭成员，我希望筛选出异常或临界读数，以便查看趋势与复诊记录。

**Acceptance Criteria:**

- **Given** 用户在历史列表页  
	**When** 选择状态筛选器（全部/健康/临界/异常）  
	**Then** 列表与统计图同步更新，并显示当前筛选条件
- **And** 导出按钮生成对应筛选结果的 CSV
- **And** 若无匹配数据，显示友好空状态与建议

**Prerequisites：** 故事 3.2。

**Technical Notes：** 后端增加查询参数 `status`; SQLAlchemy 查询按枚举过滤；前端使用 AntD `Segmented` 控件；导出遵循 UTF-8 BOM。

## 总结

* 史诗 1 将按“草稿 → 预览 → 发布”流程提供完整的阈值治理闭环，并通过导航与权限调整确保入口清晰、审计可追踪。
* 史诗 2 负责阈值在后端服务、缓存与外部接口中的一致性，Self/自己 保护策略在此阶段落地。
* 史诗 3 将提升家庭成员的录入体验与可视化洞察，让异常读数更易识别。
