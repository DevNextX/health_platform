# Requirement: 既往病史检查报告附件闭环（MVP）

## 1. 背景与价值
- **需求背景**：当前系统已具备既往病史基础 CRUD（`/api/v1/medical-history`）与前端 `MedicalHistory` 页面，但病史条目尚不支持“检查报告附件”管理，导致用户无法将关键佐证材料（图片/Word/PDF）与病史关联保存。
- **用户故事**：作为家庭健康平台用户，我希望在新增/编辑病史时上传检查报告，并在后续可查看列表、下载与删除附件，以便完整保存病史依据并便于复查。
- **业务价值**：
  - 提升既往病史信息完整性，从“文本记录”升级为“记录 + 证据材料”。
  - 降低用户在多系统/多渠道分散存储医疗报告的成本。
  - 为后续“按个人健康记录汇总、报告合并、检索增强”建立数据基础。

## 2. 与现有模块关系
- 本需求是对**既有病史模块**的能力增强，不替代现有病史 CRUD。
- 依赖现有病史主流程：
  - 后端病史资源：`/api/v1/medical-history`
  - 前端页面：`MedicalHistory`
- 附件必须与“具体病史条目”关联，不新增独立的健康档案中心页（MVP 不涉及）。

## 3. 范围与边界
### 3.1 In-Scope（首期 MVP）
- 病史附件闭环能力：
  1. 上传附件（支持图片/Word/PDF）
  2. 附件列表展示（基于病史条目）
  3. 附件下载查看
  4. 附件删除
- 支持在病史新增后持续维护附件（增删查下载）。
- 保持与当前成员上下文一致（附件归属跟随病史与成员）。

### 3.2 Out-of-Scope（明确不做）
- 全文检索（包括附件内容检索）
- OCR 识别
- 健康档案汇总导出（ZIP/PDF）
- 跨病史条目的自动报告合并
- 智能分类/标签推荐

### 3.3 后续演进方向（非本期交付）
- 面向个人维度的健康记录汇总视图（聚合病史及附件）
- 多报告合并导出（ZIP/PDF）
- 基于内容/元数据的增强检索能力

## 4. 验收标准（AC）
- [ ] **AC1 上传能力**：用户可在病史场景上传附件，支持图片、Word、PDF 三类文件；每条既往病史记录最多上传 10 个附件，超出上限时应阻止继续上传并给出明确提示。
- [ ] **AC2 列表可见**：用户可在对应病史条目下看到附件列表，至少可识别附件名称与上传时间（或等效信息）。
- [ ] **AC3 下载可用**：用户可对已上传附件执行下载，并成功在本地打开。
- [ ] **AC4 删除闭环**：用户可删除附件，删除后列表中不再出现且不可继续下载。
- [ ] **AC5 关联正确**：附件与病史条目绑定，切换病史条目时仅展示对应附件。
- [ ] **AC6 权限正确**：用户仅可访问自己有权限成员下的病史附件，越权访问被拒绝。
- [ ] **AC7 兼容现有流程**：附件能力上线后，不影响既有病史新增/编辑/删除主流程可用性。
- [ ] **AC8 失败提示明确**：上传失败、下载失败、删除失败时，用户可获得明确可理解的错误提示。

## 5. 非功能要求（NFR）
- **安全与隐私**：
  - 附件属于敏感健康资料，必须沿用现有鉴权与数据隔离策略。
  - 禁止未授权访问他人或其他家庭成员附件。
- **可用性**：
  - 上传、下载、删除操作反馈及时，状态可感知（成功/失败/处理中）。
  - 文案清晰，避免用户误删或误判状态。
  - 当单条病史附件数达到 10 个时，前后端都必须阻止继续上传，并提示已达上限。
- **兼容性**：
  - 支持主流浏览器对图片/Word/PDF 文件的下载行为。
  - 中文与英文界面文案需一致可理解（遵循现有 i18n 规范）。
- **性能**：
  - 常规附件操作应保持可接受响应时间，不显著拖慢 MedicalHistory 页面主流程。
- **可靠性**：
  - 附件元信息与病史关联关系应稳定、可持续读取，不出现“孤立附件”对用户可见。

## 6. 风险与缓解
| 风险 | 影响 | 缓解策略 |
|---|---|---|
| 用户上传文件类型与预期不一致 | 上传失败率上升，体验差 | 在上传前明确提示支持格式，并在失败时给出可执行指引 |
| 附件误删导致资料丢失感知 | 用户信任下降 | 删除动作增加确认提示，文案明确不可恢复（若产品确认） |
| 附件数量增长影响病史页面可用性 | 列表加载与操作效率下降 | MVP 先保证基础可用，后续评估分页/筛选优化 |
| 权限边界处理不一致 | 产生隐私与合规风险 | 以既有成员与病史权限模型为唯一准绳进行验收 |

## 7. 待确认项
- 附件上传入口是否仅在“编辑病史”可见，还是“新增病史流程中也可直接上传”。
- 单文件大小上限是否需要在 MVP 明确。
- 删除附件是否需要二次确认弹窗及操作审计展示。
- 附件列表默认排序规则（按上传时间倒序或其他）。
- Word 格式范围是否限定为 `.doc/.docx`（建议明确）。

## 9. 本次补充约束
- 单条“既往病史”记录的检查报告附件上限为 10 个。
- 该上限属于明确的业务规则，不是仅前端展示规则；后端接口必须做最终校验。
- 用户删除附件后，可继续补充上传，前提是删除后的当前有效附件数小于 10。
